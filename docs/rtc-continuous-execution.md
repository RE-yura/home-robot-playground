## 失敗の原因（記録の数値で確認したもの）

1. **前の計画に合わせる補正（RTC guidance）が掴みを狂わせる。** 補正ありでは指を閉じた後の開度が 0.0〜0.3（空振り）になり、掴み直しを繰り返して台車が押し流された。同じ条件で補正を切ると開度0.6（コップを保持）で止まり、真上に持ち上げた。補正の上限を10→5→2と弱めるほど成功が増え、最良は補正なし。
2. **計画の末尾が実行されず、手を離せない。** 手を離す指令は計画全体（1.6秒）をかけて少しずつ開くランプで、実際に指が開き始めるのは末尾の数コマ。計画を途中で次に切り替えると末尾が実行されず、かごに押し付けたまま離さない。次の撮影までに各計画を12コマ以上実行することで解消。
3. **やりかけの動作の巻き戻し。** 方策は実測の関節状態だけを入力とし、直前に出した指令を知らない。指が閉じきる前（約0.4秒）に撮った画像から作った計画は「まだ掴んでいない」と判断し、手を開き直して掴み直そうとする。推論中に進む時間を短くすると減る。

不採用：補正（全上限で補正なしより悪い）、切り替え直後にグリッパー指令の逆戻りを止める規則（3/10）、指の急な開閉の後に撮影を待つ規則（5/10。待ちが長引き同じ場面で数十回待つ試行があった）。いずれも補正なし同条件（7/10）を上回らなかったためコードから外した。

## 画面での使い方

- 自律操作画面（`?mode=learned`）の既定（2026-10-29、6a73962）は、v9（`prefix-rtc-v9`）の連続実行で、第2段の最終評価と同じ設定（推論中に物理を 0.4秒進める、指の開閉で止めない、返事の遅れの猶予 3コマ、コップは壁の内側の判定）。「設定」→「連続実行（推論中も動き続ける）」を外すか、URL に `&executor=sync` を付けると同期実行。従来の公開モデルは `&model=public`、元の判定は `&success=rim`。
- 日本語の指示からの計画実行（LLM）に使える。LLM を使わない単体の運搬は `?mode=learned&direct=1`（試行スクリプト用、2026-10-26 の画面再構成以降）。再生速度は画面右下に表示する。
- 指の開閉時に物理を止める規則（ハイブリッド）は既定で無効（6a73962 まではこれが既定で、`&gripPause=0` で無効にしていた）。`&gripPause=1` で有効になる。
- 手元に候補モデルを置いた場合は `&model=delay-shift`（連続実行専用。同期実行では開始を拒否する）、`&model=prefix-rtc`・`&model=prefix-rtc-e5`（同じ重みの5段版）・`&model=prefix-rtc-v2`（遅れ0〜8で再学習）・`&model=prefix-rtc-v2-e5`（その5段版、同期判定 8/10 で未評価）（同期・連続の両方で使える）で選べる。モデルはハッシュで固定した登録表（`src/learning/learned-onnx-contract.ts` の `LEARNED_CANDIDATES`）にあるものだけ選べる。指定しなければ v9（6a73962 より前は公開モデル）。
- `&rtcCoverage=<ms>` で推論中に進む物理時間を変えられる（既定 400。6a73962 より前は 200）。16コマの計画では遅れ7コマ（約600ms）が上限。数値でない値や上限を超える値では、連続実行を有効にしても開始を拒否し、理由を表示する（同期実行に切り替えて動かすことはしない）。成功が最も多かったのは `&model=prefix-rtc-v2&gripPause=0&rtcCoverage=400`（23/30、約0.47倍）、再生が最も速く 100N 以下の成功も最も多いのは `&model=prefix-rtc-e5&gripPause=0&rtcCoverage=400`（21/30、約0.69倍）。数値は 82a5e2c の画面で測ったもの（現在の画面での確認は後述）。
- `&assist=1` はルールの補助（段階6、2026-10-27）。計測値（腕の上下関節・指の開き）と経過時間だけを見て、掴み損ねが2回続くか、開始（または再開）から35秒たっても終わらないときに、腕を開始姿勢へ2秒で戻して同じモデルにやり直させる（1回の試行で最大2回）。課題の時計と採点は止めない。結果は学習モデルだけの結果とは別に、補助が働いた回数（記録の `assistEvents`）と一緒に示す。既定は無効。
- `&members=1` は速度確認用の診断。4予測の平均をやめ、1予測のグラフを1回だけ実行する。
- 第2段（2026-10-27）で足した診断用オプション。`rtcHold` 以外は既定で無効で、記録の `rtcSchedule`・`members`・`noise` に残り、`final_summary.py` は設定の違う試行を同じ行にまとめない。
  - `&rtcHold=N`（0〜5）：推論の戻りが遅れて予定の目標が尽きたとき、すぐ打ち切らずに直前の目標を最大 N コマ保って返事を待つ。保った回数は記録の `lateHolds`。6a73962 から既定は 3（0 で無効）。
  - `&noise=zero`：全予測を雑音ゼロから始める（出力が決まる）。`&members=1` と組み合わせると推論が約3割速い。v3 の連続 0.4秒では 18回中9回で、既定（30回中27回）より悪く不採用（同期は 8/10）。
  - `&rtcExec=N`：N コマ実行したら次を撮る（既定は min(12, 16−遅れ)）。再生速度は変わらない。v3 で 6 にすると 6回中2回（台車ずれ3回）で不採用。
  - 結果と診断は `docs/evidence/mug-phase2-diagnosis-2026-10-27.json`。
- 調査用の RTC 検証画面（`?mode=rtc`）では URL で条件を変えられる：`rtcCoverage`（推論中に進む物理時間 ms）、`rtcExec`（次の撮影までの実行数）、`rtcGuide=0`（補正なし）、`rtcGraph=max10|max5|max2`（補正の上限）。補正上限5・2のグラフは `tools/vla-train/rtc_onnx.py` の `max_gain` で公開グラフから再生成でき、ハッシュは `src/learning/rtc-contract.ts` に固定している。
